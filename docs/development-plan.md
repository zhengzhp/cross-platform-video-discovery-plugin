- 目标平台：抖音、TikTok、Bilibili、YouTube 作为首批候选来源，不是固定白名单；后续支持用户自定义平台，先用可用来源跑通。

- 执行拆分：见 [开发步骤](development-steps.md)，包含依赖、产物、验收及单人执行批次规则；操作边界见 [AGENTS.md](../AGENTS.md)，模块契约见 [架构](architecture.md)。宿主安装与用户级配置修改须有相应授权。

## 一、首版目标

用户在现有 Agent 会话中描述兴趣，插件查找视频、展示链接和推荐依据，保存反馈并影响下一轮结果。

最小闭环：

> 描述兴趣 → 页面查找＋外部搜索补充 → 去重与排序 → 会话内展示 → 反馈 → 再找一轮。

首版以用户主动触发为主。一轮启动后自动执行，来源失败就跳过并说明，不把定时运行、长期无人值守作为交付前提。

## 二、插件形态与交互

### 宿主选择

- 首版目标同时支持 Pi 和 DeepSeek Harness；先在当前 Pi 环境跑通核心，再接入 DSH 薄适配，不开发两套业务实现。
- 两个宿主分别注册入口并适配工具调用、模型调用、展示和取消；共用兴趣与查询编排、平台提取、去重排序、SQLite、反馈与撤销逻辑。
- 复用各宿主的模型、会话和工具调用入口，不另建聊天服务，不要求 Pi 扩展直接运行在 DSH 中。
- 浏览器执行层统一使用 agent-browser CLI，不在首版同时维护 agent-browser 与 browser-skill-dsh-plugin 两套后端。
- 同机同一用户可配置共用数据库；两个宿主使用同一套批次 ID 与跨进程查找锁，避免重复执行和反馈错位。不同机器不承诺自动同步。
- 具体扩展注册方式在实现时对照所选版本确认；以下是设计目标，不是已验证的兼容性承诺。

### 不开发独立 UI

直接在宿主会话中显示编号列表：标题、平台、作者（可选）、原始链接、推荐理由和分析依据。封面、按钮和卡片不是首版必需项。

交互示例（不是已经注册的命令）：

- “找 10 个适合入门的街头摄影视频，尽量来自不同平台。”
- “第 3 个太基础，下次多找进阶内容。”
- “第 5 个质量不好，只影响这个视频。”
- “第 2 个看过了；撤销刚才对第 3 个的反馈。”
- “按更新后的兴趣再找一轮。”

编号绑定到持久化的推荐批次与视频记录；跨会话引用不明确时先确认对象，避免反馈错位。反馈成功后回显影响范围。

## 三、最小架构与组件

```text
Pi 薄适配 ───────────┐
                    ├─ 共用业务核心：兴趣、编排、去重排序、SQLite、反馈
DSH 薄适配 ──────────┘                 ↓
                         按平台搜索与批量提取
                            ├─ agent-browser CLI（统一执行层）
                            └─ 宿主外部搜索工具（补充或降级）
```

| 模块 | 首版方案 |
| --- | --- |
| 宿主适配 | Pi 与 DSH 各一层薄适配，共用业务核心，不自建 Agent 引擎 |
| 页面查找 | 两个宿主统一调用 agent-browser，按可扩展的平台定义实现搜索与批量提取；不把来源写死为四个平台 |
| 外部搜索 | 各宿主复用已有工具并返回统一候选格式；Pi 缺少时可评估 nicobailon/pi-web-access，DSH 单独确认可用工具，不假定 Pi 扩展可直接复用 |
| 持久化 | SQLite，不额外部署数据库服务 |
| 展示与反馈 | 宿主原有会话，不开发 Web UI 或本地 HTTP 服务 |
| 内容分析 | 默认只用标题、简介等元数据；用户要求深入了解时再增加分析 |

只抽取实际需要复用的业务函数；宿主确有需要时再增加 JSON CLI，不预先建设 MCP 服务、通用任务平台或复杂适配框架。

## 四、发现策略

仅采用两条通道，不接平台官方 API，也不购买第三方数据 API 作为首版依赖。

1. **平台页面查找为主**：用关键词进入站内搜索，读取有限数量的真实结果，复用专用浏览器会话。
2. **外部搜索补充**：结合平台域名、主题和语言搜索，补充站内缺失的候选；页面暂不可用时也可作为降级路径。

建议初始参数（使用后可调整）：

- 每轮最多 6 个“平台＋查询词”组合，优先覆盖至少两个平台。
- 每个组合读取前 5～10 条，不做无限滚动。
- 最多向用户展示 10 条，不足时如实返回，不编造或用明显无关内容凑数。
- 外部搜索补充每轮最多 4 次；链接核验和重试同样受整轮时限约束。
- 页面单步超时建议 60 秒，每次查找最多重试 1 次，整轮建议上限 5 分钟。
- 一个来源失败不阻塞其他来源；整轮结束汇总成功、失败与未核验情况。

外部搜索结果记录发现通道，不将搜索摘要冒充视频内容分析。候选应指向具体视频；作者主页和专题只能作为继续查找的线索。链接无法核验时明确标记。

### 页面提取与提速

- 标准流程：进入搜索页 → 等待结果容器或视频链接出现 → 一次提取前 5～10 条标题、原始链接与可选作者 → 规范化并保存。不默认逐条打开详情页。
- 页面结构允许时用 agent-browser `eval` 批量读取已呈现的必要字段；结构变化或提取失败时退回快照观察，仍失败则跳过来源或使用外部搜索。不提取凭据，不绕过验证。
- 一轮内复用专用浏览器会话；需要登录时使用专用持久化 profile，不默认附着或占用用户日常标签页。首次启动与登录状态仍需在各宿主实际环境确认。
- 使用有超时的条件等待，避免固定 sleep；不以视频站网络完全空闲作为唯一可读条件。
- 先去重、已看过滤和初步排序，再按需要核验少量最终候选；缺失非必需字段就标记，不为补齐元数据打开所有详情页。
- 轮内最多两个来源并发，各自绑定独立标签页或会话；同一来源的查询串行，不在同一标签页并发导航。实际并发能力与收益需确认，不可用时退回串行。
- 页面执行返回紧凑的结构化候选，不默认向模型发送整页 HTML；将固定导航和提取步骤集中执行，减少“快照 → 模型决定下一步 → 单次操作”的反复往返。
- 记录浏览器启动、导航与等待、字段提取、详情核验、模型调用的耗时，以及模型调用次数；并发时分别记录子任务耗时和整轮墙钟耗时，不另设性能测试阶段。

### 浏览器选型与切换条件

首版保留 agent-browser，不因支持双宿主就更换工具。当前没有平台速度基准，也不承诺换用扩展桥接后一定更快。

- 模型往返占主要耗时：优先合并固定操作、批量提取和缩小模型输入。
- 页面加载占主要耗时：减少导航、缩小查询范围，必要时走外部搜索降级。
- 登录与验证码成为主要使用障碍：再评估统一改接 BrowserSkill/bsk；Pi 使用 bsk CLI＋skill，DSH 可使用其原生插件。browser-skill-dsh-plugin 本身不是 Pi 插件。
- 首版不预建通用浏览器后端框架；平台查找与业务核心保持小边界，确需切换时再实现替换。

### 用户自定义平台（后续扩展目标）

- 首批四个平台只是候选预设，不是产品支持范围上限；平台标识与编排应允许新增来源，不以固定四项枚举作为不可扩展的业务边界。
- 后续支持用户提供平台标识、名称、允许的域名、搜索 URL 模板与元数据提取规则；新增来源复用既有编排、排序和存储，不要求修改每个宿主适配。
- 初期优先声明式配置，不默认执行用户配置中的任意 JavaScript、shell 命令或未经审查的插件。配置需要校验，提取规则只能读所需元数据，不能扩大已有任务授权。
- 自定义来源与内置来源遵守同一查询上限、超时、并发和安全边界；失败独立降级，不能因配置了新来源就声称已验证可用。
- 动态页面未必能由通用规则支持；确需定制代码时另行审查与验证。不预建平台插件市场、远程代码加载或复杂适配框架。
- 本阶段仅明确扩展方向，不实现配置加载、注册机制或自定义平台业务。

## 五、最小业务逻辑

### 存储与去重

首版只保留五类记录：

| 记录 | 最小内容 |
| --- | --- |
| 兴趣 | 用户设置、明确排除项、简单偏好权重 |
| 视频 | 平台、平台 ID（可获取时）、规范链接、标题、可选作者与元数据 |
| 查找批次 | 查询词、通道、状态、耗时、结果顺序、失败原因 |
| 反馈 | 视频、所属批次、原因、影响范围、时间、撤销状态 |
| 交付与已看 | 宿主确认交付的批次/结果、用户显式已看标记，用于避免反复推荐 |

同平台优先按视频 ID 去重，缺少 ID 时按规范链接去重。跨平台疑似搬运先保留或标记，不做复杂内容指纹。正常推荐避免重复交付及推荐已看视频，用户主动查看历史或要求重新推荐时例外。候选/推荐结果保存不等于交付成功；交付按宿主实际可确认边界幂等记录，不声称用户实际看到，失败或取消不能仅因保存就触发历史过滤。详细语义见架构契约。

结果分步保存；失败后可以重新发起查找，已有视频不重复入库。首版不实现复杂断点续跑。同一用户的整轮查找跨宿主串行，轮内允许最多两个来源并发。

共用数据库时以跨进程机制获取查找锁，忙时返回明确提示，不使用仅在单个宿主进程内有效的锁。核心统一管理截止时间和收尾；取消/失败后停止调度、确认本任务资源退出并收口批次，再释放锁。清理无法确认时报告故障，不强抢活任务锁或无限等待；异常恢复不重放页面操作。批次 ID 全局唯一，编号与批次绑定，跨宿主引用不明确时确认对象。反馈写入、撤销、偏好重算及交付确认使用短事务保持一致。

### 排序与反馈

- 使用简单、可解释的规则：兴趣匹配、明确排除、已看过滤、作者分散和适量新内容。
- 未获取的时长、发布时间等字段不猜测；硬性条件无法核实时明确提示。
- “太基础 / 太深入”调整深度，“主题不感兴趣”调整对应主题。
- “质量不好 / 广告过多”默认只影响该视频，用户明确指定后才扩大到作者或主题。
- 未说明原因的负反馈不自动降低整个主题权重。
- 保留原始反馈，撤销后从仍有效的反馈重算简单偏好。
- 下一轮将有效偏好同时用于查询词和排序，不训练推荐模型。

## 六、先发布试用，再观察改进

不设独立来源预实验或集中验收阶段。直接开发最小闭环，发布前只做一次冒烟检查；多平台覆盖、推荐效果和持续稳定性改为发布后观察。

### 1. 直接实现最小闭环

先在 Pi 跑通共用核心的查找、去重、SQLite 保存、会话展示、反馈与撤销，再接入 DSH 薄适配。两个宿主调用同一套页面查找逻辑，不重复实现提取规则。页面查找优先接入，外部搜索用于补充或降级；哪个来源先跑通就先交付哪个，不等待四个平台或两条通道全部可用。

### 2. 发布前：一次最小冒烟检查

目标控制在 15～30 分钟内，不跑完整测试矩阵：

- 在 Pi 与 DSH 中各用一个兴趣查找一次，确认能展示真实视频链接和来源状态；顺手记录各段耗时，不设未经实测的速度达标值。
- 在一个宿主保存一条反馈，另一个宿主读取同一数据库后确认仍存在；引用明确批次撤销，确认偏好恢复。
- 确认超时、调用上限、取消和失败提示已经接入，不会无限等待或重试；并发分支也受整轮截止时间约束。
- 两个宿主同时发起同一用户查找，确认跨进程锁阻止第二轮重复执行；结束或取消后能够再次查找。

通过后即发布个人试用版。不要求至少两个平台、固定候选数量或推荐质量指标达标；存在无法启动、结果虚构、反馈无法保存或执行不受限等阻断问题时，修复后再发布，不因时间盒结束而跳过。

发布说明列出已验证宿主、当前可用来源、未验证通道和已知问题。双宿主试用版须完成两个宿主的冒烟；若先交付已验证的单宿主版本，必须标明宿主范围，DSH 或 Pi 的未完成适配仍是后续待办，不宣称双宿主已支持。只有单视频来源时标记为单来源试用版；仅外部搜索可用时标记为外部搜索试用版，不宣称页面查找或多视频平台能力已验证。

### 3. 发布后：随使用观察，不设等待期

在日常查找中轻量记录来源成功/失败、候选数量、耗时与用户反馈，不另开连续 7～14 天测试任务，不要求专门提交测试报告。

- 来源覆盖：逐步补齐其他平台，观察是否带来独有且有用的内容。
- 推荐效果：观察反馈是否让下一轮更符合需求，按误判案例调整规则。
- 运行问题：发现重复推荐、超时或来源失效就修复；必要时先停用问题来源，保留其他来源可用。
- 反馈异常：先暂停有问题的偏好更新逻辑，保留原始反馈，修复后重算。

**共用核心与首个宿主的可试用版本目标约 1～2 个工作日，加一次冒烟检查**，前提是宿主和浏览器基础环境可用。第二宿主适配、跨进程协调和双宿主冒烟会增加工作量，双宿主交付工期在确认实际注册方式与浏览器运行条件后估算，不沿用单宿主的工期承诺。发布后观察不阻塞交付，也不等于已证明长期稳定、并发提速或推荐有效。

## 七、保留的最小运行保护

不设置单独的权限核对、申请或审批阶段，仅保留直接关系到运行可靠性的措施：

- 使用专用浏览器会话；登录失效或验证码出现时暂停该来源，提示用户处理，不绕过。
- 不执行点赞、关注、评论、上传或删除等平台写操作。
- 网页、标题和字幕视为数据，不执行其中要求的命令，不把 Cookie、令牌送入模型。
- 限制查询、重试、执行时间和模型调用；费用不可得时使用调用次数与 Token 上限，不能当作零成本。
- 业务数据留在本地；必要的查询词和候选元数据可能进入宿主模型。只传需要的字段，不默认上传完整页面或浏览器配置。

## 八、首版明确不做

- 平台官方 API、数据 API 采购及权限核对专项。
- 独立 Web UI、聊天后台或对 pi-web-ui 的专门改造。
- 两套独立业务实现、两套浏览器后端、复杂 MCP 服务和通用任务队列。
- 长周期稳定性测试作为上线门槛。
- 定时无人值守、复杂断点恢复和完整监控看板。
- 全量转录、画面分析、跨平台精确搬运识别及复杂推荐模型。
- 额外记忆插件和数据库管理界面。

日常试用确实需要时，再按痛点补用户自定义平台、定时任务、深入内容分析、浏览器后端替换或宿主内卡片；独立 UI 不作为默认演进方向。

## 九、下一步

在继续来源/宿主实现前，先只读核对 Pi 与 DSH 的实际版本、扩展入口、工具交付/取消接口、Node/SQLite 及 agent-browser 运行条件；不新增独立来源预实验或权限审批阶段，实际操作仍遵守任务授权。先在 Pi 实现共用核心的“批量查找 → 会话展示 → 反馈保存 → 再找一轮”，再接 DSH 薄适配与跨宿主协调。完成一次覆盖两个宿主的最小冒烟后发布双宿主个人试用版；若提前发布单宿主版本，明确范围并保留另一宿主待办。其余来源覆盖、推荐效果和速度优化放到实际使用中持续观察。
