# 验证规范

脚本以 [package.json](../package.json) 为准；实际检查结果只记入 [项目状态](status.md)。下列要求区分现有检查与后续能力验收，不能用文档或类型定义证明运行保护已实现。

## 1. 按变更选择最小充分检查

已授权开发包含匹配的本地离线检查；安装依赖、真实浏览器/账号、宿主安装、用户级设置与发布仍遵守 [操作边界](../AGENTS.md)。不为了省事跳过必要断言，也不为纯文档修改默认跑真实来源。

| 变更 | 必须检查 | 不自动执行 |
| --- | --- | --- |
| 仅 Markdown 文档 | 本地链接、代码围栏、标题结构、非预期字面转义、脚本引用、事实/范围一致性；检查差异 | 类型/业务测试、浏览器与宿主冒烟 |
| core 纯逻辑/类型 | npm run typecheck；相关离线单测，结束前 npm test | 真实平台、模型调用 |
| SQLite/锁/批次/反馈 | 类型检查、npm test；覆盖事务回滚、独立进程竞争、取消/异常恢复及旧数据兼容 | 创建持久化真实业务库 |
| browser/platforms/编排（后续） | 类型检查、假执行器/页面夹具；输出与调用上限、整轮截止时间、迟到结果拒绝、资源退出后释放锁 | 附着日常浏览器、账户操作 |
| 宿主适配/交付接口（后续） | 实际版本文档/类型核对、离线适配测试；保存与交付失败分离、确认幂等 | 安装宿主插件、修改用户级配置 |
| 包配置/构建/依赖 | 锁文件一致性、类型/测试、打包预览，确认产物与隐私边界 | 依赖无关升级、发布或推送 |

新能力必须增加真实断言，不用空测试或自动 skip 冒充覆盖。测试默认离线，在临时目录使用合成数据。针对性检查不能替代该变更必须通过的全量离线验收。

## 2. 本地工程检查

Node.js 22.13+，推荐 24；有锁文件时执行 npm ci，没有锁文件的首次安装使用 npm install 并保留新锁文件。npm ci 使用现有锁文件，不声称它生成新锁。

开发和打包检查可按变更选用：

```sh
npm ci
npm run typecheck
npm test
node --check scripts/clean.mjs
npm pack --dry-run --ignore-scripts
npm run clean
```

- npm test 已包含 npm run build，再运行 build 仅用于明确需要的独立构建或示例检查，避免重复构建。
- 打包预览需包含预期模块，但不得包含数据库、profile、凭据、node_modules 或完整工具日志；产物中仍为空的宿主入口不能作为兼容性证据。
- clean 只删除 dist，不删除业务数据或其他程序资源。验证产生的临时文件自行清理，不覆盖已有工作区内容。
- Node 版本、SQLite 实验性状态及实际宿主环境分别记录；在 Node 22 的某个版本通过不能推定最低 22.13.0 或所有宿主通过。

## 3. 离线业务验收

当前 npm test 构建后执行 tests/*.test.mjs，已有用例范围见 [测试目录](../tests/README.md)。以下是对应能力的验收要求，未实现项保留待办：

- 候选/排序：规范链接、ID/链接去重、未知硬条件警告、相关性与解释、反馈范围和撤销；不将搜索摘要视为内容分析。
- 存储：持久化、稳定批次编号、事务一致性、schema 版本与迁移、重启及不同连接读取；保存候选/推荐不能自动等于交付或已看。
- 交付：保存成功但返回失败/取消、重复确认、部分交付及未确认分支；没有交付确认的结果不触发已交付过滤。
- 锁与生命周期：跨进程竞争、正常结束、取消、失败、崩溃、PID 复用或挂起状态；确认本任务资源已停止再释放，无法确认退出时不误报清理成功。
- 执行/编排：参数与域名校验、单步及整轮超时、共享预算、有限重试、来源隔离、人工处理暂停、取消后不接受迟到写入；关闭本任务资源而非用户浏览器。
- 后续自定义平台配置随业务加入校验用例，拒绝任意脚本执行；当前不提前实现配置加载。

失败要保留原因、修复与复测摘要，不削弱断言。普通离线用例通过不能代替尚未覆盖的故障分支。

## 4. 宿主与真实来源冒烟

先只读核对目标宿主与 CLI 版本及运行条件，不另建长期来源预实验。获得相应操作授权后，按实际交付范围执行一次最小冒烟，目标 15～30 分钟：

- 每个宣称支持的宿主实际加载、查找并交付真实具体视频链接，来源状态与未核验情况如实显示。
- 双宿主交付才要求同数据库跨宿主反馈读取与撤销、同用户查找互斥、结束/取消后可再次查找；单宿主先交付须明确范围。
- 超时、截止时间、调用上限、资源清理和交付确认接入；登录/验证码不绕过，不执行平台写操作。
- 记录分段与整轮耗时、调用量，不预设未实测的速度或推荐效果承诺。

时间盒不是跳过阻断问题的理由；失败修复后复测。无法加载、结果虚构、反馈无法保存、执行不受限或清理不可靠时不能发布为可用版本。

## 5. 文档与交付证据

文档检查至少覆盖：

1. 所有本地 Markdown 链接存在，代码围栏成对，章节标题独占一行且层级可辨。
2. 无非预期的字面量反斜杠 n 等转义，尤其不能把正文塞进标题行；检查工具“通过”仍需人工复核语义。
3. npm run 引用对应现有脚本；拟新增脚本须标为计划，不能作为可执行快速开始。
4. 实际进度只在状态文档维护；其他文档引用它，不将目标契约或历史验证写成当前能力。
5. 对照本次开始时的工作区差异，确认未修改业务代码（文档任务）、未覆盖既有改动、未夹带秘密或产物。

状态记录检查日期、环境/版本、命令或方法、结果及未验证范围。证据关联提交（如已有）或明确为未提交工作区；更正旧结论注明原因，不声称本次重新执行了历史测试。不存完整对话、页面或工具日志。

结束报告必须区分本批完成、整体完成、暂停或阻塞，并列出停止原因（如有）、剩余项与下一步。静态检查、离线业务、实际宿主加载和真实来源冒烟分别报告，不能互相替代。
